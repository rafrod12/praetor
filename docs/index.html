How it works

A reference monitor — the security field's gold standard — rebuilt for agents and made distributed so it has no single point of compromise.

01 / MEDIATION

Complete mediation

Agents act only through the SDK's guarded() boundary. If Praetor denies, the action never runs. No direct path to tools, secrets, or other agents.

02 / QUORUM

Threshold co-signing

The orchestrator is segmented across independent nodes. High-risk actions need 3-of-5 Ed25519 co-signatures. Compromise one node — even ours — and you get nothing.

03 / SPEED

Tiered consensus

Routine reads get single-use capability tokens — no round trip. Only consequential actions pay the quorum cost. Consensus on the exception path, not the hot path.

04 / PROOF

Tamper-evident audit

Every approve and deny is hash-chained. Edit history and the chain breaks — detectably. Checkpoints anchor externally so even the operator can't rewrite the past.

One line at the action boundary

No re-architecture. Wrap the action; Praetor authorizes, then your code runs — or it doesn't.

from praetor import Orchestrator, PraetorClient

orch  = Orchestrator(node_count=5, threshold=3)
agent = PraetorClient(agent_id="agent-alpha", orchestrator=orch)

# High-risk: requires 3-of-5 nodes to co-sign before release_funds() runs.
agent.guarded("payment", "bank://acct/990 -> vendor/acme",
              perform=lambda: release_funds(),
              metadata={"amount": 250_000, "currency": "USD"})

FAQ

Doesn't a central broker add latency?

Only where it matters. Low-risk actions use locally-verifiable capability tokens — no round trip. The m-of-n quorum fires only on high-risk actions (payments, deletes, external tools, secret access), which are rare by construction.

Isn't the broker itself a single point of failure?

No — that's the whole design. The orchestrator is segmented across independent signing nodes. Authorization requires a threshold (default 3-of-5) of valid co-signatures. One compromised or dead node can neither approve an action nor block the cluster.

What happens when the quorum is unreachable?

Fail-closed for anything new or risky. The demo shows this live: with only 2 of 5 nodes alive, a payment is denied and the denial is logged.

Do you see our data or hold our credentials?

No. The data plane runs in your environment and the orchestrator brokers action metadata and decisions, not payloads. Credentials stay in your vault; Praetor issues short-lived, scoped capability tokens.

Is this just a service mesh / API gateway?

A mesh routes bytes. Praetor reasons about agent actions: it classifies intent, enforces per-action least privilege, cryptographically co-signs the risky ones, and emits an agent-attributed, tamper-evident audit trail.

How does this make money if it's open source?

The proven OSS model: the data plane (this repo) is free forever. The paid control plane adds managed multi-host quorums, policy management, identity issuance, compliance exports, and support.
